Profile Cross-App Sync — Website Side

Grant's Estate Agents website · docs/plans/2026-10-02-1510-feat-profile-cross-app-sync-plan.html

1. What and why

Confirmed with the GEA app project: saves, open-home registrations, and enquiries all already share one Supabase backend across the website and the iOS app. But the website's own profile page and lead-capture route don't fully use what's there yet. Three concrete gaps, all fixable without touching the shared schema:

  1. Profile page hydrates saved-property detail from localStorage instead of fetching by id — so a property saved on the app doesn't appear on the web profile.
  2. Profile page has no "your open home registrations" section at all, despite the data being fully queryable per user_id.
  3. The website's lead-capture route (/api/lead) emails property enquiries straight through Resend and never writes to the shared enquiries table — so a property enquiry made on the website never shows in anyone's profile, on either app, and bypasses the CRM pipeline the app already uses.

3. Decisions

DecisionOutcome
Which lead types move to enquiriesdecided Only property-enquiry. It already carries a real property_id and the server already resolves address/agent from it (resolvePropertyDetails in route.ts) — a clean fit for type: 'inquiry'. contact and market-report have no property context and don't fit the schema; appraisal would need the type check extended (out of scope here, see §6) — all three stay on the existing Resend-only path for now.
Resend email for property-enquirydecided Drop the direct Resend call for this type once the enquiries insert lands — the notify-enquiry trigger already emails the agent via the shared CRM path. Keeping both would double-email the agent on every property enquiry.
Anonymous visitorsdecided Still allowed. user_id is nullable on enquiries and anon insert is confirmed to work; write user_id when createClient() resolves a session, leave it null otherwise. No sign-in wall added to the enquiry form.

4. Website-side tasks

4.1 Fix saved-properties hydration on the profile page

src/app/profile/page.tsx currently loads full property data from localStorage.getItem('savedPropertiesData') (lines ~19-31). Replace with: for each id in savedPropertyIds (from useSavedProperties, already Supabase-backed), fetch /api/properties/[id] in parallel and build the display list from the responses. Drop the localStorage read entirely — it's the actual bug, not a fallback worth keeping.

4.2 Add an "Open home registrations" section to the profile

  • New Supabase query (client-side, via useAuth's user.id, or server component if the page is restructured): open_home_registrations for the current user, joined to open_home_snapshots on open_home_id for address/date/time.
  • New tab alongside "Saved Properties" / "Saved Searches" (matches the existing tab pattern in profile/page.tsx), listing registered inspections with status, linking each to /property/[id].
  • Empty state: "You haven't registered for any open homes yet," matching the existing empty-state style for saved properties.

4.3 Route property enquiries through the shared enquiries table

In src/app/api/lead/route.ts, for type === 'property-enquiry', after resolvePropertyDetails resolves address/agent:

const supabase = createClient(); // src/lib/supabase/server.ts — cookie-aware, anon fallback
const { data: { user } } = await supabase.auth.getUser();

const { error } = await supabase.from('enquiries').insert({
  type: 'inquiry',
  property_id: propertyId,
  property_title: details.address,
  agent_email: details.agentEmail,
  name, email, phone,
  message: extra.message ?? null,
  user_id: user?.id ?? null,
});
if (error) {
  // fall back to the existing Resend path rather than silently losing the lead
}
  • Keep the existing GA4 trackLeadConversion call unchanged.
  • Keep a Resend fallback path only for insert failure (never fake success, per this route's existing policy) — don't send Resend when the insert succeeds, to avoid double-notifying the agent.
  • Rate limiting, honeypot, body-size cap, and field allow-listing all stay exactly as they are — this only changes where a successful property-enquiry submission is delivered.
  • contact, appraisal, market-report types are untouched — same Resend-only path as today.

5. Explicitly out of scope

  • Any Supabase schema or migration change — not owned by this repo (§2 flag).
  • Moving contact, appraisal, or market-report leads onto the enquiries table.
  • Building a unified "saved / registered / enquired" timeline UI beyond three separate profile sections — a combined feed is a nice-to-have, not needed to close the gaps raised.
  • Changing anything in the app project itself.

6. Follow-up asks back to the app project (not blocking this plan)

  • Add a source text default 'app' column to enquiries (website would write 'web') so enquiry origin is distinguishable in the CRM/reporting.
  • If appraisal requests should also flow through the shared CRM path, extend the type check constraint to allow 'appraisal' — only needed if/when that migration ships; website's appraisal form stays on Resend-only until then.
